# SOC/DFIR Platform & Live Cyber Range Workstation

> **Автономная рабочая станция расследования инцидентов (Live SOC/DFIR Workstation) и платформа киберучений (Cyber Range)** на базе высокопроизводительного микроядра Rust и локального интерфейса расследований.

---

## 🚀 О проекте

Платформа спроектирована по принципу **Evidence-Driven Investigation** и **Local First**: все артефакты, процессы, сокеты, сетевые связи и криминалистические данные собираются непосредственно с анализируемой системы и локальной инфраструктуры без синтетических макетов и передачи данных во внешние облака.

### Ключевые возможности

- 🔍 **Live Windows Host Telemetry**: Полный слепок хоста в реальном времени:
  - Дерево процессов с иерархией `Parent-Child`, командными строками и SHA-256 хэшами.
  - Активные сетевые сокеты TCP с привязкой к PID, локальным и удаленным адресам.
  - Точки закрепления (Autorun в реестре Run/RunOnce, Запланированные задачи).
  - Инвентаризация системных служб с детекцией уязвимостей путей (`Unquoted Service Path`).
- 🌐 **Сетевое обнаружение (Network Discovery)**:
  - Парсинг системного кэша ARP и таблицы маршрутизации Windows.
  - Определение активных сетевых интерфейсов, шлюзов по умолчанию и подсетей.
  - Быстрое параллельное TCP-сканирование портов критических сервисов.
- 🛡️ **Поиск CVE в ОС и установленных пакетах** (раздел «Уязвимости»):
  - Linux: пакеты dpkg/rpm сопоставляются с бюллетенями дистрибутива из **OSV** (Debian, Ubuntu, AlmaLinux, Rocky Linux) с учётом бэкпортов: версии сравниваются по правилам dpkg/rpm.
  - Windows: выпуск и сборка ОС (с номером обновления, UBR) и установленные KB сопоставляются с ежемесячными бюллетенями **Microsoft MSRC** (CVRF): для каждой CVE видно, какой сборки и какого KB не хватает. Поддерживаются Windows 10/11 и Windows Server 2012–2025, включая Server Core и hotpatch-обновления.
  - Для каждой CVE: установленная версия, версия с исправлением (или «исправления нет»), оценка дистрибутива или Microsoft, **CVSS v3**, **EPSS**, флаг **CISA KEV** и отметка Microsoft об эксплуатации в атаках.
- ⚡ **Детерминированный движок корреляции**:
  - Потоковая оценка наблюдений (`Observation`) с автоматическим выводом верифицированных фактов (`Fact`).
  - Комплекс правил `CORR-WIN-001` .. `CORR-WIN-004` (дамп LSASS, офисные шеллы, запуск из Temp/Public, подозрительный C2 трафик).
  - Привязка к тактикам/техникам **MITRE ATT&CK** и уровням **Пирамиды боли (Pyramid of Pain)**.
- 📊 **Интерактивный Forensic UI**:
  - Чистый стартовый baseline без учебного шума (`0 моковых находок`).
  - Реактивное наполнение при сборе реальных улик.
  - Инспектор карточек находок (**Drill-Down Inspector**) с детальным техническим обоснованием.
  - Временная шкала расследования (Timeline) и матрица MITRE ATT&CK.
  - Криминалистическое хранилище артефактов с двойным хэшированием (**CAS BLAKE3 + SHA-256**) и реляционная база **SQLite (WAL)**.

## 🏛️ Архитектура платформы

Проект организован в виде модульного Cargo-workspace (`#![forbid(unsafe_code)]` во всех модулях предметной области):

```text
soc-dfir-platform/
├── apps/
│   └── desktop-ui/           # Локальный Forensic UI (HTML5, Vanilla JS, CSS Glassmorphism)
├── crates/
│   ├── core-domain/           # Эпистемическая модель: Fact, Inference, Hypothesis, Observation
│   ├── platform-windows/      # Сбор телеметрии Windows (PowerShell/WMI, реестр, сокеты)
│   ├── platform-linux/        # Сбор телеметрии Linux (/proc, netlink, sysfs)
│   ├── privilege-broker/      # Типизированный брокер привилегированных операций + аудит-лог
│   ├── normalization-engine/  # Парсинг EVTX/PCAP, генерация CPE 2.3/PURL, сопоставление CVE
│   ├── correlation-engine/    # Детерминированный корреляционный движок и правила находок
│   ├── graph-engine/          # Граф атак и взаимосвязей сущностей
│   ├── timeline-engine/       # Временные дорожки событий и артефактов
│   ├── taxonomy-projection/   # Проекция находок на таксономию/Pyramid of Pain
│   ├── evidence-engine/       # Работа с криминалистическими объектами улик
│   ├── tool-adapters/         # Парсеры внешних форматов (EVTX/PCAP) для инструментов
│   ├── workflow-dag/          # Планировщик задач с DAG-зависимостями и лимитами ресурсов
│   ├── storage-cas/           # Контентно-адресуемое хранилище артефактов (BLAKE3)
│   ├── storage-sqlite/        # Реляционное хранилище расследований (SQLite WAL)
│   ├── ipc-protocol/          # JSON-RPC 2.0 протокол взаимодействия UI и движка
│   ├── engine-server/         # Диспетчер IPC, корреляция, кейс-менеджмент, коллаборация
│   ├── desktop-app/           # Нативный десктопный бинарник (Tao/Wry WebView)
│   ├── scenario-engine/       # Загрузка и проверка подписи сценариев Cyber Range
│   ├── scenario-verifier/     # Сверка результатов игрока со сценарием
│   ├── scoring-engine/        # Пояснимый скоринг сценариев (§17.2)
│   ├── diagram-engine/        # Построение диаграмм атак
│   └── report-engine/         # Формирование сводки инцидента по фактам и графу
└── docs/                      # Детальная инженерная документация
```

> Часть возможностей out of scope для текущей версии: снятие дампа памяти
> процесса и захват сетевого трафика (`AcquireMemorySample`/`CapturePcap`)
> сознательно возвращают явную ошибку "не реализовано" вместо имитации
> результата — захват пакетов требует установленного Npcap. Приложение
> работает с одним локальным хостом и одной учётной записью владельца;
> полноценные роли, шифрование и мультихост запланированы отдельным этапом.

### 🔐 Безопасность локального сервера

- Встроенного пароля нет: при первом запуске интерфейс просит задать пароль
  владельца (не короче 8 символов). Базы, созданные старыми версиями с
  паролем `admin`, тоже проходят эту настройку заново.
- Все вызовы `/rpc`, кроме `health`, `auth.status`, `auth.setup` и
  `auth.login`, требуют токен сессии (256 бит, хранится в базе только в виде
  хэша, срок жизни 7 дней). После 5 неверных паролей вход блокируется на 30 с.
- Сервер отвечает только на запросы с `Host`/`Origin` вида `127.0.0.1`,
  `localhost` или `::1` (защита от DNS rebinding и запросов с чужих сайтов),
  не выдаёт CORS-разрешений и отдаёт статику только из каталога UI.

## ⚡ Быстрый старт

- **ОС**: Windows 10/11 x64 / Windows Server 2019+
- **Rust**: версия 1.85+ (stable)
- **Node.js**: v20+ (для локальной разработки UI)

### Сборка и запуск тестов

```powershell
# Клонирование репозитория
git clone https://github.com/Sirojiddin6556/soc-dfir-platform.git
cd soc-dfir-platform

# Запуск полного набора автоматических тестов
cargo test --workspace

# Проверка линтером clippy
cargo clippy --workspace --all-targets -- -D warnings
```

### Запуск десктопного приложения

```powershell
# Сборка оптимизированного релиза
cargo build --release

# Запуск приложения
.\target\release\desktop-app.exe
```

После запуска откроется окно **Forensic Cockpit** с подключением к локальному движку по IPC.
При первом запуске задайте пароль владельца.

### Запуск только движка (браузер вместо окна)

```bash
cargo run --release -p engine-server
# затем откройте http://127.0.0.1:8080
```

### Поиск CVE в ОС и пакетах

В разделе «Уязвимости» кнопка «Обновить базу» скачивает в `SOC_DATA_DIR/vulndb/vuln.db`:
на Linux бюллетени OSV для дистрибутива этой машины (`https://osv-vulnerabilities.storage.googleapis.com/<Экосистема>/all.zip`),
на Windows бюллетени Microsoft за последние 12 месяцев (`https://api.msrc.microsoft.com/cvrf/v3.0/cvrf/<ГГГГ-Ммм>`),
а также каталог CISA KEV и оценки FIRST EPSS. Повторное обновление пропускает неизменившиеся файлы и бюллетени.
Через API глубину можно задать явно: `vulndb.update` с `{"msrc_months": 24}` (от 1 до 120; на Linux бюллетени MSRC загружаются только так).
«Проверить» заново читает список пакетов или версию и обновления Windows и показывает найденные CVE.
Если сборка старше самого раннего загруженного бюллетеня, результат об этом предупреждает: CVE более ранних месяцев не проверялись.

Без интернета положите в `SOC_VULNDB_OFFLINE_DIR` файлы с теми же данными:
`Ubuntu_24.04_LTS.zip` (или `Debian_12.zip`, `AlmaLinux.zip`, `Rocky_Linux.zip`),
бюллетени MSRC в формате JSON под именами `2026-Sep.json` (сколько угодно месяцев, скачиваются с заголовком `Accept: application/json`),
`known_exploited_vulnerabilities.json`, `epss_scores-current.csv.gz`.

### Поиск уязвимостей в исходном коде

Раздел «Анализ кода» проверяет папку с проектом на Python, Java, PHP, C/C++ и JavaScript/TypeScript на машине, где работает движок.
Он ищет путь данных от входа пользователя (параметры HTTP-запроса, сокет, переменные CGI) до опасного вызова:
SQL-инъекции, внедрение команд ОС и кода, обход каталогов, XSS, LDAP/XPath-инъекции, XXE, SSRF, шаблоны,
открытые перенаправления; а также слабые шифры и хеши, секреты в коде и отключённую проверку TLS.
Для каждой находки показаны строка кода, источник данных и все шаги пути.

- «Считать входом атакующего и аргументы командной строки, переменные окружения, stdin и файлы» нужен для утилит
  и служб на C/C++; для веб-приложений без него меньше шума.
- Остальные файлы проекта (шаблоны, JS, конфигурация, `.env`, скрипты оболочки) проверяются на секреты:
  пароли, ключи и токены по имени (`admin_password`, `SECRET_KEY`, `api_key`) и виду значения, значения
  по умолчанию в `getenv()`, пароли в вызовах подключения к БД и в строках подключения, известные форматы
  ключей (AWS, GitHub, Slack, Stripe, закрытые ключи). Значение секрета в отчёте скрыто. Секрет в `.env`
  сообщается, только если `.gitignore` не исключает этот файл. В итогах видно, сколько файлов каждого вида
  проверено и какие не проверялись (двоичные, минифицированные, слишком большие).
- Для веб-приложений (Flask, FastAPI, Django, Spring, сервлеты, страницы PHP) строится модель: какие маршруты
  есть, на какие методы они отвечают, проверяют ли вход по cookie или сессии, меняют ли данные, читают ли
  пароль, ставят или удаляют cookie входа. Из неё следуют находки: изменение данных без токена CSRF (Django и
  Spring Security проверяют его сами, JSON-запросы чужой формой не отправить), изменение данных и выход по
  GET-запросу, вход без ограничения попыток, публичная форма, которая пишет в БД без лимита запросов и капчи,
  текст сообщения из адреса (`?error=…`), показанный как надпись сайта, страницы без
  X-Frame-Options/`frame-ancestors`, cookie входа, собранная из одних констант. Страница PHP считается закрытой
  входом, если подключает файл, который проверяет сессию. В любом коде: ключ, токен или подпись из запроса,
  сравнённые обычным `==`, пароль под быстрым хешем (MD5, SHA-1, SHA-256, `h.update()`, HMAC с постоянным
  ключом, в том числе с постоянной солью и в функции-хешере из другого модуля), пароль под медленным хешем с
  постоянной солью (PBKDF2, scrypt, bcrypt, `PBEKeySpec`, `hash_pbkdf2`), запись всех полей формы в цикле любого
  вида без списка разрешённых, шаблон, скомпилированный из данных БД (сохранённая SSTI), `int()` или
  `Integer.parseInt()` от ввода без обработки ошибки (ответ 500), пустой `except`/`catch` вокруг проверки
  (fail-open) или вокруг запуска и подключения к БД, файл SQLite или H2 по пути от текущей папки. Страницей
  считается маршрут, который рендерит шаблон сам или через свою вспомогательную функцию.
- Сторонние библиотеки проверяются на известные уязвимости (CVE, GHSA) и вредоносные версии по базе OSV.
  Пакеты берутся из файлов зависимостей (`requirements*.txt`, `pyproject.toml`, `Pipfile(.lock)`, `poetry.lock`,
  `uv.lock`, `pdm.lock`, `package.json`, `package-lock.json`, `yarn.lock`, `pnpm-lock.yaml`, `composer.json/.lock`,
  `pom.xml`, `build.gradle(.kts)`, `gradle.lockfile`, `go.mod`, `Cargo.lock`, `Gemfile.lock`, `*.csproj`,
  `packages.config`, `packages.lock.json`), из виртуального окружения Python, `node_modules` и `vendor` в папке
  проекта, из скопированных в проект JS-библиотек (jQuery, Bootstrap, Angular, lodash и др. по заголовку файла) и из
  ссылок на CDN в страницах. Версии сравниваются по правилам каждой экосистемы (PEP 440, SemVer, Maven, Composer,
  RubyGems, NuGet). Уязвимая версия показывается находкой «Уязвимая зависимость» (CWE-1395) на строке, где она
  задана, со списком уязвимостей, ссылками на OSV и версией, которая закрывает все; пакет из бюллетеня о вредоносном
  ПО (MAL-*) показывается как «Вредоносный пакет» (CWE-506). Базу для нужных экосистем загружает кнопка в блоке
  «Зависимости» (PyPI около 35 МБ, npm около 210 МБ, остальные по 3–12 МБ); без интернета положите в
  `SOC_VULNDB_OFFLINE_DIR` файлы `PyPI.zip`, `npm.zip`, `Maven.zip` и т. п. Пакеты без точной версии и модули
  Python, которые код импортирует без списка зависимостей, перечислены отдельно: их версии неизвестны.
- Тесты по умолчанию не проверяются: их число показано в итогах, флажок «Проверять и тесты» включает их.
- В C/C++ кроме путей данных ищутся ошибки памяти и чисел: переполнение буфера и чтение за его границей,
  разыменование NULL и непроверенный результат `malloc()`, использование памяти после `free()` и повторное
  освобождение, целочисленное переполнение (CWE-190/191) в арифметике над числами, которые дал пользователь,
  в том числе над полями структуры, прочитанной из сокета или файла. Без входа пользователя о числах сообщается
  только для знаковых констант, выходящих за свой тип: беззнаковые хеши и счётчики переполняются намеренно.

Тот же анализ из командной строки:
`cargo run --release -p code-analysis --example scan -- ПАПКА [--json] [--tests] [--external]`.
В API: `code.scan` с `{"path": "...", "external_sources": false, "include_tests": false}`, затем `code.status`;
базу для зависимостей загружает `vulndb.update` с `{"ecosystems": ["PyPI", "npm"]}`, после неё `code.deps` проверяет
зависимости последнего анализа заново.

### Проверка запущенного сайта

Раздел «Запущенный сайт» проверяет работающее веб-приложение целиком (DAST): по его адресу движок обходит
страницы и формы в пределах того же сайта, при необходимости сначала входит, и проверяет найденные
параметры вживую, отправляя тестовые запросы и читая ответы.

- Поиск эндпоинтов. Кроме обхода ссылок движок перебирает встроенный словарь частых путей (как ffuf) и
  находит страницы и API, на которые нет ссылок, — это нужно для одностраничных приложений, где обход ссылок
  не даёт ничего. Чтобы не принять за находку общий «шаблон-заглушку», сначала запрашивается заведомо
  несуществующий путь, и адрес считается найденным, только если ответ отличается от него. Если сайт отдаёт
  описание OpenAPI/Swagger (например `/openapi.json`), движок читает его и проверяет каждый документированный
  эндпоинт с его параметрами, включая JSON-тело запроса.
- Вход. По HTML-форме (с подстановкой скрытых полей вроде CSRF-токена) или по JSON-API: логин отправляется
  как JSON, а возвращённый токен (`access_token` и т.п.) движок запоминает и шлёт в заголовке `Authorization:
  Bearer` на последующих запросах.
- Активные проверки: отражённый XSS (CWE-79) — внедрённый тег возвращается без экранирования; SQL-инъекция
  (CWE-89) — одиночная кавычка вызывает ошибку базы данных, которой не было без неё; обход каталога (CWE-22) —
  в ответ попадает содержимое системного файла; открытое перенаправление (CWE-601) — параметр уводит браузер
  на внешний адрес. Проверяются параметры запроса, поля форм и поля JSON-тела у эндпоинтов из OpenAPI.
  XSS и SQL-инъекция проверяются во всех параметрах, обход каталога и перенаправление —
  в тех, чьё имя или значение похоже на файл или адрес.
- Пассивные проверки ответов: нет Content-Security-Policy, нет защиты от кликджекинга (X-Frame-Options или
  `frame-ancestors`), нет `X-Content-Type-Options: nosniff`, нет HSTS на HTTPS, cookie без флагов HttpOnly,
  Secure, SameSite, раскрытая версия ПО в заголовках `Server`/`X-Powered-By`.
- Каждая находка показывает запрос, который её вызвал, в виде команды `curl`, чтобы повторить вручную.
- Сканер не выходит за пределы указанного адреса, ограничивает число страниц и запросов и представляется
  отдельным `User-Agent`. Отправка форм (может изменить данные) и активные проверки включаются флажками.
  Указывайте только тот сайт, который вам разрешено проверять.

Тот же сканер из командной строки:
`cargo run --release -p web-scan --example scan -- URL [--json] [--no-active] [--no-forms] [--no-discover] [--no-openapi] [--login URL --field имя=значение ... --login-json --success ТЕКСТ]`.
В API: `web.scan` с `{"url": "http://...", "active": true, "submit_forms": true, "discover_paths": true, "use_openapi": true, "login": {"url": "/api/login", "username": "...", "password": "...", "user_field": "email", "json": true, "success_text": "..."}}`, затем `web.status`.

### Docker

```bash
docker compose -f config/docker/docker-compose.yml up --build
# http://localhost/ ; для доступа по другому имени: SOC_PUBLIC_HOST=имя docker compose ...
```

В контейнере живой осмотр хоста видит сам контейнер, а не машину с Docker.
Для анализа кода смонтируйте проект в контейнер только для чтения (пример есть в `docker-compose.yml`)
и укажите в разделе путь внутри контейнера, например `/scan/shop`.

### Сквозной тест в настоящем браузере

```bash
cargo build -p engine-server
cd apps/desktop-ui && npm install --no-save playwright && npx playwright install chromium
node scripts/e2e-real-engine.mjs
```

Тест запускает настоящий `engine-server` на временной базе и проходит интерфейс в
Chromium: первичная настройка, вход и выход, загрузка EVTX, сбор данных о хосте,
все разделы. Любая ошибка в консоли или на странице считается провалом.
